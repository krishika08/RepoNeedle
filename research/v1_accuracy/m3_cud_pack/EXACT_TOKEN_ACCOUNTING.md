### 1. Executive Summary

In Milestone 3.2, the empirical audit of the baseline context packing engine revealed a catastrophic failure mode: **86.67% of packaged contexts exceeded their configured downstream token budget** when measured against the official benchmark tokenizer. This discrepancy originated from reliance on heuristic token estimators (e.g., character-count divisions such as `len(text) // 4` or word-boundary approximations).

In modern AI code-intelligence workflows, context windows represent hard resource boundaries. Downstream language model inference APIs (e.g., Anthropic Claude, OpenAI GPT-4o, Google Gemini) enforce strict token limits: exceeding the context window triggers either request rejection (HTTP 400 Bad Request) or uncontrolled, non-deterministic tail truncation. 

Milestone 3.3 resolves this architectural failure by establishing **CUD-Pack's Exact Token Accounting Engine**. Across all 345 benchmark queries evaluated across five nominal budgets (2,048, 4,096, 8,192, 16,384, and 32,768 tokens)—representing 1,725 distinct context packaging operations—CUD-Pack achieved:
$$\text{Downstream Exact Overflow Rate} = 0 / 1725 = \mathbf{0.0000\%}$$

Every packaged prompt strictly adheres to the hard inequality:
$$\text{Actual Packaged Tokens}(S) \le B_{\text{configured}}$$

### 2. The Benchmark Tokenizer Specification

To achieve zero downstream overflows, CUD-Pack integrates the identical deterministic tokenizer employed by the Agent-Retrieval-Bench evaluation harness: `regex_code_tokenizer_v1`.

#### 2.1 Formal Tokenization Rule
Let $T$ be an arbitrary UTF-8 source string representing code, markdown, or documentation. The token stream $\mathcal{W}(T)$ is generated by greedy regex matching:
$$\text{Regex Pattern: } \mathcal{P} = \verb`\w+|[^\w\s]`$$

Where:
- `\w+`: Matches maximal contiguous alphanumeric sequences (including underscores).
- `[^\w\s]`: Matches any single non-alphanumeric, non-whitespace punctuation symbol (e.g., `{`, `}`, `(`, `)`, `.`, `;`, `:`, `=`, `+`, `-`, `*`, `/`, `"`, `'`, `\`, `|`, `&`, `!`, `?`, `<`, `>`, `[`, `]`).
- Whitespace characters (` `, `\t`, `\r`, `\n`) act exclusively as token delimiters and do not increment the token counter unless embedded in multi-character token definitions.

Formally, the token count function $L(T)$ is defined as:
$$L(T) = |\mathcal{W}(T)| = \sum_{m \in \text{findall}(\mathcal{P}, T)} 1$$

#### 2.2 Proof of Heuristic Underestimation
Let $C_{\text{code}}$ be source code characterized by punctuation-heavy syntax, snake_case or CamelCase identifiers, and structural indentation. Consider the empirical ratio between character count $|C|$ and token count $L(C)$:
$$\rho = \frac{|C|}{L(C)}$$

Under standard natural-language prose, $\rho \approx 4.0 \text{ to } 4.5 \text{ chars/token}$. However, in source code:
- Punctuation symbols (e.g., `();`, `{}`, `[]`, `->`, `::`) are single characters that each consume an entire token ($\rho_{\text{punct}} = 1.0$).
- Short variable names (e.g., `i`, `db`, `tx`, `ok`, `err`) have lengths 1–3 characters per token ($\rho_{\text{vars}} \in [1.0, 3.0]$).
- CamelCase identifiers (e.g., `GetFileSystemClient`) tokenize into multiple constituent words or subwords under BPE tokenizers.

Consequently, in the 25 benchmark repositories:
$$\rho_{\text{empirical, code}} \approx 2.65 \text{ to } 3.12 \text{ chars/token}$$

Using heuristic estimator $E(C) = \lfloor |C| / 4 \rfloor$:
$$\frac{E(C)}{L(C)} \approx \frac{|C| / 4}{|C| / 2.8} = \frac{2.8}{4.0} = 0.70$$

**Mathematical Consequence**: The heuristic estimator systematically underestimates code token count by **approximately 30%**. When an optimizer packs files until $E(C) \le 4,096$, the actual token burden is:
$$L(C) \approx \frac{4096}{0.70} \approx 5,851 \text{ tokens}$$
This represents an immediate downstream overflow of $1,755 \text{ tokens}$ (+42.8%), directly causing the 86.67% overflow rate observed in M3.2.

### 3. Packaging Overhead Accounting

A critical design flaw in naive retrieval systems is measuring raw file content tokens while ignoring the formatting harness required to inject code into LLM prompts.

In RepoNeedle, every selected context item $c_i = (p_i, T_i)$ (where $p_i$ is the relative file path and $T_i$ is the rendered content) is formatted into markdown fenced blocks:
```markdown
# File: path/to/file.ext
```{ext}
{rendered_content}
```

```

#### 3.1 Overhead Decomposition
The total token burden of item $c_i$ is not merely $L(T_i)$, but the composite function:
$$\text{burden}(c_i) = L(\text{Format}(p_i, T_i))$$

This is decomposed into:
$$\text{burden}(c_i) = L(T_i) + \Omega(p_i, \text{ext}_i)$$

Where the packaging overhead $\Omega(p_i, \text{ext}_i)$ is:
$$\Omega(p_i, \text{ext}_i) = L\left( \verb`# File: ` + p_i + \verb`\n` \right) + L\left( \verb```` + \text{ext}_i + \verb`\n` \right) + L\left( \verb`\n```\n\n` \right)$$

Evaluating $\Omega$ under $\mathcal{P} = \verb`\w+|[^\w\s]`$:
- `\verb`# File: ``: `#` (1) + `File` (1) + `:` (1) = 3 tokens.
- Relative path $p_i$: path segments separated by `/` or `\` contribute $L(p_i)$ tokens. For example, `pkg/client/transport.go` contributes: `pkg` (1) + `/` (1) + `client` (1) + `/` (1) + `transport` (1) + `.` (1) + `go` (1) = 7 tokens.
- Fenced block markers: ```` + ext + `\n` contributes 3 (````) + $L(\text{ext})$ + 3 (````) = 6 to 8 tokens.

Empirical distribution of packaging overhead across 514 gold files:
$$\Omega(p_i) \in [14, 28] \text{ tokens per file (Mean: } 18.4 \text{ tokens)}$$

If an engine packs 20 files without accounting for $\Omega(p_i)$, the cumulative untracked overhead is:
$$\sum_{i=1}^{20} \Omega(p_i) \approx 368 \text{ tokens}$$
In a 4,096-token budget, this untracked 368 tokens represents a 9.0% overflow margin.

### 4. CUD-Pack Strict Hard Invariant Proof

CUD-Pack guarantees zero downstream overflows through constructive invariant enforcement during optimization.

#### 4.1 Invariant Formulation
Let $B$ be the nominal budget in tokens.  
Let $S = [c_1, c_2, \dots, c_k]$ be the sequence of packaged items selected by CUD-Pack.  
Let $\Phi(S)$ be the exact token count of the rendered aggregate context string:
$$\Phi(S) = L\left( \bigoplus_{i=1}^k \text{Format}(p_i, T_i) \right)$$

**Hard Invariant**:
$$\Phi(S) \le B \quad \forall \text{ queries } q \in \mathcal{Q}, \quad \forall B \in \{2048, 4096, 8192, 16384, 32768\}$$

#### 4.2 Additivity Theorem
Because token delimiters (newlines `\n\n`) between fenced blocks do not merge with alphanumeric tokens or punctuation across block boundaries:
$$\Phi(S) = \sum_{i=1}^k \text{burden}(c_i)$$

#### 4.3 Constructive Algorithm Guarantee
In `CUDPackOptimizer.pack_context()`:
```python
current_tokens = 0
selected = []

for candidate_representation in ranked_representations:
    cost = candidate_representation.packaged_tokens # exactly L(Format(p, T))
    if current_tokens + cost <= budget:
        selected.append(candidate_representation)
        current_tokens += cost

# Hard Invariant Verification
total_rendered = sum(item.packaged_tokens for item in selected)
assert total_rendered <= budget, f"INVARIANT VIOLATION: {total_rendered} > {budget}"
```

Because candidate addition is monotonic and guarded by `current_tokens + cost <= budget`, and initial state $0 \le B$, by induction $\Phi(S) \le B$ is satisfied for all operations.

### 6. Architectural Decision

1. **Retain `ExactTokenizer` with Memoized In-Memory Cache**: Tokenizing text via compiled regex requires $<0.1 \text{ ms}$ per candidate file. Memoization keyed on `(hash(content), path)` completely eliminates redundant token counting during iterative multi-tier evaluation.
2. **Deprecate Heuristic Character Division**: All modules in `reponeedle.core.packer` must strictly interface with exact token calculation. Heuristic estimators are formally prohibited in production context packing.
