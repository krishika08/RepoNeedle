## 1. EXECUTIVE SUMMARY

This audit provides a forensic evaluation of the benchmarking methodology, candidate-generation universe, metric definitions, and evaluation scripts used in Stage 3.4 (`878ff68`) and Stage 3.5 (`4f78cc3`).

The investigation resolved three major discrepancies that previously corrupted the research record:
1. **The Recall@20 Baseline Discrepancy**: Stage 3.5 silently substituted **Binary Hit@20** ($195/345 = 0.5652$) for **Multi-Target Fractional Recall@20** ($0.5078$), artificially distorting the comparisons against Stage 3.4.
2. **Artificial Candidate Pool Restrictions**: Stage 3.5 evaluated `code2test` with `tests_only = True`, eliminating code distractors. On the mandatory 100% unconstrained candidate pool, Candidate F collapses from $0.2152$ to **$0.1351$ MRR** (substantially below pure BM25 at $0.1735$).
3. **Hardcoded Evaluation Bypasses**: The reported $1.0000$ MRR on `BurntSushi/ripgrep` was generated by hardcoded string path checks in `reponeedle/core/graph.py:425-435`. When excised, Candidate F achieves $0.0000$ on that fixture due to missing manifest context in the 2-file synthetic snippet.
4. **Hardcoded RepoMap Reference Constant**: The Stage 3.5 report cited a fixed constant of $0.2140$ MRR for RepoMap from an older v1.1 subset. Live evaluation of official RepoMap on all 345 ARB v2 queries achieves **$0.2293$ MRR** and **$0.6599$ Recall@20**, decisively outperforming Candidate F.

## 2. THE BASELINE METRIC DISCREPANCY RECONCILIATION

### 2.1 The Discrepancy
| Retrieval System | Stage 3.4 Recall@20 | Stage 3.5 Recall@20 | Stage 3.6 Canonical Fractional Recall@20 |
| :--- | :---: | :---: | :---: |
| **Internal BM25** | `0.4467` | `0.4928` | **`0.4549`** (Full Pool) / `0.4467` (Chunk Pool) |
| **RepoMap (Aider)** | `0.6306` | `0.5681` | **`0.6599`** (Full Pool) / `0.6306` (Chunk Pool) |
| **Candidate C** | `0.5516` | `0.5516` | **`0.5105`** (Full Pool) |
| **Candidate F** | *Unbuilt* | `0.5652` | **`0.5078`** (Full Pool) |

### 2.2 Mathematical Cause: Hit@K vs Fractional Recall@K
In ARB v2, tasks have multiple gold targets ($|\text{gold}_i| \ge 1$):
- **Multi-Target Fractional Recall (Canonical Contract)**:
  $$\text{Recall@K}_{\text{frac}} = \frac{1}{N} \sum_{i=1}^N \frac{|\text{gold}_i \cap \text{ranked}_{i, :K}|}{|\text{gold}_i|}$$
- **Binary Hit@K (Stage 3.5 Erroneous Metric)**:
  $$\text{Hit@K}_{\text{bin}} = \frac{1}{N} \sum_{i=1}^N \mathbb{I}(|\text{gold}_i \cap \text{ranked}_{i, :K}| \ge 1)$$

Forensic recalculation across all $N=345$ positive queries confirms:
- **BM25 in Stage 3.5**: Exactly $170$ queries had at least one target in top 20:
  $$\frac{170}{345} = 0.4927536\dots \approx \mathbf{0.4928}$$
- **RepoMap in Stage 3.5**: Exactly $196$ queries had at least one target in top 20:
  $$\frac{196}{345} = 0.5681159\dots \approx \mathbf{0.5681}$$
- **Candidate F in Stage 3.5**: Exactly $195$ queries had at least one target in top 20:
  $$\frac{195}{345} = 0.5652173\dots \approx \mathbf{0.5652}$$

Stage 3.5 calculated binary Hit@20 and erroneously reported it in the table column labeled "Recall@20". When true multi-target fractional recall is computed, RepoMap achieves **0.6599**, whereas Candidate F achieves only **0.5078**.

## 3. CANDIDATE UNIVERSE FAIRNESS & CANDIDATE POOL RESTRICTIONS

### 3.1 Stage A (Generation) vs Stage B (Ranking)
A fair evaluation requires that all systems be evaluated against the complete repository file universe:
- **Stage 3.4/3.5 Flaw**: The candidate generator restricted the candidate pool for `code2test` tasks by passing `tests_only = True`. This eliminated non-test files from the pool, artificially removing code distractors.
- **Stage 3.6 Canonical Protocol**: Every system must rank against the **full candidate corpus** (code + test + documentation + configs) without pre-filtering.

### 3.2 Impact of Unconstrained Candidate Universe
When evaluated against the 100% unconstrained candidate pool:
- Candidate F MRR collapses from `0.2152` $\to$ **`0.1351`**.
- Pure BM25 MRR is **`0.1735`**.
- Candidate F is **statistically inferior to BM25** ($p = 0.0483$).
- Document length inflation from appending polyglot regex symbols penalizes true targets under BM25 length normalization ($b = 0.75$).

## 4. CONTEXT PACKING BUDGET ACCOUNTING RECONCILIATION

In Stage 3.5, two different BCY@8k figures were published for Candidate F:
- Main Ranking Table: `BCY@8k = 0.3184`
- Context Packing Experiment: `BCY@8k = 0.3835`

### Cause of the Discrepancy
- `0.3184` was computed across **all 345 queries** in ARB v2, including zero-yield queries (queries where no gold file was ranked or packed).
- `0.3835` was computed exclusively over the subset of queries where **at least one relevant target was retrieved and packed into the budget**.
- **Audit Standard**: To maintain scientific comparability, all summary yield metrics must be reported over the full benchmark population ($N=345$). Reporting yield only over successful retrievals biases the measurement.

## 5. SUMMARY OF AUDIT FINDINGS

1. The Stage 3.4 vs Stage 3.5 baseline discrepancies are **100% resolved and mathematically explained**.
2. Stage 3.5's claimed superiority of Candidate F over RepoMap was an artifact of:
   - Comparing Candidate F Hit@20 against RepoMap Hit@20 while mislabeling both as Recall@20.
   - Using a hardcoded static constant ($0.2140$) for RepoMap MRR.
   - Restricting candidate distractors in `code2test`.
   - Hardcoding Ripgrep bypasses in `reponeedle/core/graph.py`.
3. Under the canonical, unconstrained evaluation protocol, **Authoritative RepoMap decisively outperforms Candidate F across all ranking and packing metrics** ($p < 0.0001$).
